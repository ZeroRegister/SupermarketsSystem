\chapter{SYSTEM TESTING}
\section{Functional test}
The backend integration suite runs 27 cases against MySQL and Redis containers. It covers anonymous denial, CSRF, role boundaries, invalid input, duplicate SKU, threshold hierarchy, stock receipt, dispatch, signed adjustment, count-to-zero, unchanged stocktake, insufficient stock, exact replay, changed-payload conflict, concurrent dispatch, concurrent identical submission, warning thresholds, recovery, acknowledgement, archive, manager threshold access, and last-administrator protection. All 27 cases passed.

The frontend includes three threshold-boundary unit tests. The browser suite records 14 checks: login, dashboard, inventory, history, warning, report and team views, empty search, actual stock receipt submission, manager acknowledgement, role-protected deep links, and 390-pixel viewport containment. It completed with zero JavaScript runtime errors.

\section{Performance test}
The warning query benchmark alternates cache and bypass order across three rounds. Each mode has 20 warm-up and 200 measured sequential requests per round, producing 600 samples per path. The cached path has a pooled median of approximately 5.33 ms and the MySQL bypass path approximately 6.56 ms. The comparison is descriptive and local; it includes session, revision, network, JSON, Redis, and database work.

\section{Failure and recovery test}
The Redis service was stopped while MySQL remained available. A cache-enabled warning query returned the same warning identifiers, quantities, and reviewer data as the uncached baseline. Redis was restarted and the result remained equivalent. A separate restart fingerprint showed unchanged product and transaction rows after application restart. These tests support fallback and ordinary persistence, not disaster recovery or production availability.
\section{Test discussion}
The tests validate the selected implementation boundaries rather than every possible real-world condition. They do not include a store user study, hardware failure, disk corruption, multi-node deployment, fractional quantities, expiry batches, or a production point-of-sale integration. The strongest defensible statement is that the current release satisfies its defined single-store acceptance scenarios in the recorded environment.
