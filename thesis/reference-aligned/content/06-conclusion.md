# Conclusion
Shelfwise implements an inventory and stock-warning workflow for a single supermarket. The application ties each product balance to the stock movements that produced it and ties each shortage to a persisted warning episode. A responsive Vue interface gives administrators, managers and clerks access to different operations, while the Spring Boot server and the MySQL database remain responsible for authorization and durable change. Redis serves only as an optional page cache, never as a second source of business truth.

The first question asked how quantity changes can remain bounded, explainable and resistant to duplicates. The design answers it with a locked product read, server-derived arithmetic, a mandatory actor and reason, actor-scoped key uniqueness and a single coordinating transaction. Integration cases cover receipts, dispatches, corrections, absolute counts, rejected operations, replay and concurrency; in the concurrent-dispatch case, twelve attempts against seven units produce exactly seven successes and a final balance of zero.

The second question concerned the interpretation of warnings. The system keeps shortage, batch-age, slow-moving and recovery conditions apart from reviewer attribution. Tests cover zero stock and threshold equality, healthy replenishment, renewed shortage, batch expiry boundaries, sales-only slow-moving detection and concurrent acknowledgement, which records the first reviewer without altering stock. Clock-controlled tests of recovery expiry and cache visibility remain the most important gap in this part of the evaluation.

The third question concerned role-specific access. Endpoint rules separate catalog administration, routine stock posting and managerial review, browser navigation mirrors these boundaries, and integration cases confirm that unauthorized server requests are refused. The enabled flag and role are reloaded on every request. A wider deployment would add rate limiting, credential recovery, multi-factor authentication, shared session handling and a broader security assessment.

The fourth question concerned the evidence for performance and recovery. In the preserved warning-query benchmark of six hundred sequential samples per path, the pooled median is 5.33 ms with Redis enabled and 6.56 ms with the cache bypassed. The distributions overlap, and both paths include the revision and authentication work that the cache cannot remove. A recorded Redis interruption returned equivalent warning data, and an ordinary application restart preserved the selected stock and movement rows. These observations support the chosen local mechanisms but establish neither capacity, disaster recovery nor a production availability target.

The engineering contribution is the integration of audited stock changes, batch allocation, warning lifecycles and reviewed purchasing in a runnable single-store application, with requirements, source excerpts and test assertions exposing the relevant transaction and permission boundaries. The resulting records keep catalog edits, stock movements, physical observations and managerial decisions distinct.

Further development should address fractional quantities and rounding, event identity and reconciliation for point-of-sale integration, supplier terms and lead times, and multi-store isolation, each with its own ledger records and acceptance cases. Operational evaluation should examine real staff workflows, larger concurrent workloads, cache-expiry boundaries, cross-product key races, database deadlocks and restore procedures.
