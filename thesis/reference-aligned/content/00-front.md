# Work overview
## Research purpose and objectives
This project designs, implements and evaluates Shelfwise, a web-based inventory and stock-warning system for a small supermarket. The system links every product balance to the operations that produced it and gives each member of the store team a view of stock health suited to their role. The work centers on the reliability of everyday inventory tasks: receiving a delivery, dispatching goods, correcting a discrepancy, recording a physical count and reviewing a shortage.

The objectives are to define the requirements and role permissions, design a relational stock model, implement the browser client and transactional server, and evaluate normal operations, invalid requests, retries, concurrent access and selected failures. Versioned migrations, pinned dependencies, executable tests and preserved evaluation records make the results reproducible.
## Engineering contribution
The contribution is an integrated treatment of stock consistency and warning interpretation. Product-level pessimistic locking serializes accepted changes, and actor-scoped idempotency keys separate a repeated request from a new operation. A persisted warning lifecycle keeps shortage, recovery and acknowledgement apart, while revision-based cache keys accelerate warning pages without giving Redis any durable authority. Each mechanism is well established on its own; the contribution lies in combining them, stating their invariants explicitly and evaluating how they interact within a bounded supermarket workflow.
## Deliverables and implementation scope
The deliverables are the Vue 3 browser application, the Spring Boot service, the MySQL schema, the Redis warning-page cache, a Docker Compose deployment, executable tests, captured interfaces and this thesis. The application serves one store and supports integer quantities, batch receipts, FEFO/FIFO dispatch, expiry and slow-moving warnings, replenishment suggestions, purchase approval with partial receipts, reviewed counts and disposal, and three fixed roles. Phone access is provided by the responsive web application; no native Android or iOS application or embedded firmware is delivered. Checkout, payment settlement, supplier invoicing and multi-store isolation are outside the implemented scope.
## Thesis organization
The introduction sets out the problem, objectives and evaluation questions. Chapter 1 analyzes the inventory domain, and Chapter 2 derives the requirements, reviews related systems and justifies the technology choices. Chapter 3 develops the architecture, persistence model and consistency mechanisms. Chapter 4 presents representative interfaces and the critical implementation paths, and Chapter 5 evaluates functionality, concurrency, performance and recovery. The conclusion relates the findings to the research questions. The appendices document the API contracts, the acceptance catalog and the reproduction procedure, while supplementary materials hold the complete figure and schema collections.
# Abstract
A small supermarket needs to know not only how much stock it holds but also how that quantity came about. Editing a quantity directly can hide mistakes, and resending a request after a network interruption can apply the same stock change twice. A warning system becomes misleading as well if reviewing a shortage is treated as if the product had been replenished. This thesis develops Shelfwise, a single-store inventory and stock-warning application that addresses these problems with an auditable transaction path and an explicit warning lifecycle.

The application combines a Vue 3 and TypeScript browser client with a Spring Boot server on Java 21. MySQL stores products, users, stock movements, batches, warning episodes, stock reviews and purchasing records, and Redis provides a revision-keyed cache for warning pages. Within a single transaction, each accepted stock change locks the product row, validates an actor-scoped idempotency key, checks quantity bounds, allocates dispatches first-expiry-first-out (FEFO) with a first-in-first-out (FIFO) fallback for undated batches, updates warning episodes and advances the cache revision. Expiry rules follow the configured business timezone, slow-moving rules consider sales only, and purchasing separates drafting, submission, managerial approval and partial receipt. Three fixed roles divide administration, managerial review and operational stock work, and the request path is protected by session authentication, cross-site request forgery (CSRF) tokens and server-side authorization.

The evaluation comprises 45 passing backend integration cases and three passing frontend threshold tests. Recorded browser journeys exercise the rendered views, a stock receipt and a managerial acknowledgement, and a separate capture run confirms role navigation and responsive layout without posting business data. In a preserved local benchmark of 600 measured requests per mode, the Redis-enabled warning query has a median latency of 5.33 ms against 6.56 ms for the cache-bypass path; these figures describe a small sequential workload rather than production capacity. Recorded Redis interruption and application restart checks support the cache fallback and ordinary data persistence.

The result is a runnable system in which stock changes, batch allocation, warning transitions, purchasing decisions and human review remain distinct and inspectable. The study is limited by demonstration data, integer quantities, manually maintained thresholds and suppliers, a single application node and the absence of a study with store users. The design provides a basis for point-of-sale integration, fractional units, multi-store isolation, supplier integration and operational evaluation.

Keywords: inventory management; stock warning; transactional consistency; idempotency; role-based access control; responsive web application.
# Introduction
A stock balance is useful only when staff can trust it. An employee checking a shelf needs to know whether the recorded quantity reflects the latest deliveries and dispatches, whether a correction has already been applied and whether a colleague has noticed a shortage. A manager investigating a discrepancy needs a different view of the same facts: which operation changed the quantity, who performed it, what reason was given and whether the shortage later recovered. Data consistency and the explanations offered by the interface are therefore two sides of the same requirement.

Consistency must also hold when requests are repeated or arrive concurrently. A duplicate submission can record one receipt twice, and two dispatches can both draw on the same displayed balance. Batch expiry separates physical stock from sellable stock, and purchase receipts and cached warning pages must agree with every accepted write. These cases shape the transaction, warning and cache controls implemented in Shelfwise.

The study addresses four questions. First, how can quantity changes remain bounded, auditable and resistant to duplicate submission? Second, how should shortage and recovery be represented so that they are not confused with human acknowledgement? Third, how can a browser interface offer role-appropriate operations while authorization remains the responsibility of the server? Fourth, what evidence supports the behavior of the system under its stated local workload and failure scenarios? These questions guide the design and the acceptance tests in the following chapters.

The work is conducted as a bounded software case study. Each requirement is traced to API routes, data structures, user operations and test assertions. Design diagrams describe the implemented classes and migrations, interface images show the running application, and code excerpts cite their source locations. Test suites and preserved measurement records form the basis for evaluating each requirement.

The implementation is a modular monolith deployed as four Docker Compose services. A Spring Boot container coordinates stock, warning, review and purchasing transactions; Nginx serves the compiled Vue client and proxies API requests; MySQL stores durable state; and Redis caches warning-page responses. Keeping the business logic in one service allows related inventory changes to complete within a single database transaction.
