\FloatBarrier

\section*{Research purpose and objectives}

\addcontentsline{toc}{section}{Research purpose and objectives}

The purpose of this project is to design, implement and evaluate a Web-based inventory and stock-warning system for a small supermarket. The system, named Shelfwise, connects the current product balance to the operations that created it and gives different members of the store team an appropriate view of stock health. Its central problem is the reliability of everyday inventory work: receiving a delivery, dispatching products, correcting a discrepancy, recording a physical count and reviewing a shortage.


The objectives are to establish the domain and its operating boundaries; define functional requirements and role permissions; design a relational model for products, movements and warning episodes; implement a responsive browser client and transactional server; and evaluate normal operations, invalid requests, retries, concurrency and selected service failures. A further objective is reproducibility. The database migration, dependency versions, test scripts, figure sources and original evaluation records accompany the implementation so that another reader can inspect how the reported behavior was obtained.


\FloatBarrier

\section*{Engineering contribution}

\addcontentsline{toc}{section}{Engineering contribution}

The contribution is an integrated engineering treatment of stock consistency and warning interpretation. Product-level pessimistic locking serializes accepted changes. Actor-scoped idempotency keys distinguish a repeated request from a new operation. A persisted warning lifecycle distinguishes shortage, recovery and acknowledgement. Revision-based cache keys allow warning pages to be accelerated without assigning durable authority to Redis. These mechanisms are established techniques; the work contributes their application, explicit invariants and evaluated interaction within a bounded supermarket workflow.


A useful result is the separation of operational facts. A received delivery changes quantity, a physical count records an observation, and acknowledgement records a review. The interface and database preserve these differences instead of treating all three as changes to an editable stock field. The project therefore makes a stock number explainable in terms of actor, reason, time and before-and-after quantities.


\FloatBarrier

\section*{Deliverables and implementation scope}

\addcontentsline{toc}{section}{Deliverables and implementation scope}

The deliverables comprise the Vue 3 browser application, Spring Boot service, MySQL schema, Redis warning-page cache, Docker Compose deployment, executable tests, captured interfaces and this thesis. The application supports one store, integer sellable quantities, batch receipts, FEFO/FIFO dispatch, expiry and slow-moving warnings, replenishment suggestions, purchase approval and partial receipts, reviewed counts and disposal, and three fixed roles. The phone-sized interface is the responsive Web application; no native Android or iOS application and no embedded firmware are delivered. Checkout, payment settlement, supplier invoicing and multi-store isolation remain outside the implemented scope.


\FloatBarrier

\section*{Development and verification work}

\addcontentsline{toc}{section}{Development and verification work}

The project work comprises domain modeling, requirement analysis, architecture and schema design, backend and frontend implementation, security configuration, local deployment and evidence-based evaluation. The documented tests include the current backend integration suite, frontend boundary tests, an earlier browser acceptance journey and the later figure-capture verification. Performance and recovery observations are drawn from dated local records. This scope describes the available project work rather than a real-store trial or a production deployment.

\chapter*{Abstract}

\addcontentsline{toc}{chapter}{Abstract}

A small supermarket requires both a current inventory position and an explanation of how that position arose. Directly editing a quantity can obscure errors, while repeating a request after a network interruption can duplicate a stock change. A warning system also becomes misleading when reviewing a shortage is treated as equivalent to replenishing the product. This thesis develops Shelfwise, a single-store inventory and stock-warning application that addresses these concerns through an auditable transaction path and an explicit warning lifecycle.


The application combines a Vue 3 and TypeScript browser client with a Spring Boot and Java 21 server. MySQL stores products, users, stock movements, batches, warning episodes, stock reviews and purchasing records. Redis provides a revision-keyed warning-page cache. Accepted stock changes acquire a product row lock, validate an actor-scoped idempotency key, check quantity bounds, allocate dispatches by FEFO where batch data exists, update warning episodes and advance the cache revision within a transaction. Expiry rules use the configured business timezone, slow-moving rules inspect sales-only history, and purchasing separates draft, submission, managerial approval and partial receipt. Three fixed roles divide administration, managerial review and operational stock work. Session authentication, CSRF protection and server-side authorization protect the request path.


Evaluation includes 27 passing backend integration cases and three passing frontend threshold tests. Recorded browser journeys exercise rendered views, a stock receipt and managerial acknowledgement. A separate screenshot-capture run confirms role navigation and responsive layout without posting new business data. A historical local benchmark contains 600 measured requests per mode: the Redis-enabled warning query has a median response latency of 5.33 ms, compared with 6.56 ms for the cache-bypass path. These observations describe a small sequential workload, not production capacity. Recorded Redis interruption and application restart checks support cache fallback and ordinary data persistence.


The result is a runnable system in which stock changes, batch allocation, warning transitions, purchasing decisions and human review remain distinct and inspectable. The study is limited by demonstration data, integer quantities, manually maintained thresholds and suppliers, one application node and the absence of a store-user study. The design provides a basis for later work on point-of-sale integration, fractional units, multi-store isolation, external supplier integration and operational evaluation.


Keywords: inventory management; stock warning; transactional consistency; idempotency; role-based access control; responsive Web application.


\chapter*{Introduction}

\addcontentsline{toc}{chapter}{Introduction}

A stock balance is useful only if staff can rely on it when making an operational decision. A supermarket employee checking a shelf needs to know whether the recorded quantity reflects recent deliveries and dispatches, whether a correction has already been applied, and whether a colleague has noticed a shortage. A manager investigating a discrepancy needs a different view of the same facts: which operation changed the quantity, who performed it, what reason was recorded and whether the shortage later recovered. These requirements link data consistency to the explanation presented by the interface.


The engineering problem is therefore broader than product creation and retrieval. A client can submit twice, two staff members can dispatch from the same product balance, an expired batch can be physically present but unsellable, a recovery warning can be confused with a shortage, a purchase can be received twice, and a cached page can outlive the write that should replace it. Each case can produce a believable interface while the underlying meaning is wrong. Shelfwise is organized around explicit treatment of these cases rather than around a large list of retail features.


The study asks four questions. First, how can quantity changes remain bounded, auditable and resistant to duplicate submission? Second, how should shortage and recovery be represented without confusing them with human acknowledgement? Third, how can a browser interface expose role-appropriate operations while the server remains responsible for authorization? Fourth, what evidence supports the behavior of the system under its stated local workload and failure scenarios? These questions determine the design and the acceptance tests discussed in the following chapters.


The development approach uses a bounded case study. Requirements are mapped to routes, data structures, user-facing operations and test assertions. Design diagrams are derived from the implemented classes and migration. Interface images are captured from the running application. Code images retain their source locations. Evaluation uses the actual test suites and preserved measurement records. This connection between requirements, implementation and evidence allows the reader to assess an engineering result without assuming business benefits that were not measured.


The implementation is a modular monolith packaged as a four-service Docker Compose deployment. A Spring Boot container owns stock, warning, review and purchasing transactions, while an Nginx container serves the compiled Vue client and proxies API requests. MySQL is authoritative and Redis is disposable. Batch inventory, warning policies and purchasing workflows are implemented within the same transaction-aware service boundary. This arrangement fits the single-store scope; it does not establish a distributed inventory platform, accounting ledger or point-of-sale system.
